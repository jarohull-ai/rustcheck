# rustcheck

[![CI](https://github.com/jarohull-ai/rustcheck/actions/workflows/ci.yml/badge.svg)](https://github.com/jarohull-ai/rustcheck/actions/workflows/ci.yml)

Sandboxed Rust compile verification for code you did not write — mainly code
generated by an LLM.

The loop it exists for:

```
model → code → rustcheck → { pass | error codes + spans } → model repairs
```

## Why not just run `rustc`?

`rustcheck` does the same type-check (`rustc --emit=metadata`, ~40 ms), but adds
the four things an agent loop needs:

1. **Isolation** — the compiler runs under `bwrap` with no network, no write
   access outside a tmpfs, and `--die-with-parent` (when bwrap is installed).
2. **A hard timeout** — macro bombs and hangs are killed instead of stalling
   the pipeline.
3. **No pipe deadlock** — stdout/stderr are drained by reader threads, so a
   large diagnostic dump cannot block the child process.
4. **Structured diagnostics** — `--json` returns error codes, levels and
   line/column, parsed from rustc's own JSON stream instead of regex over text.
5. **Dependencies** — `--dep serde` builds the crate's rlibs with Cargo once,
   caches them, and passes them to `rustc` as `--extern`, so snippets that use
   the registry are type-checkable without a project of their own.

## Install

```bash
cargo install --path .
```

## Use

```bash
# from a file
rustcheck check src/snippet.rs

# from stdin, warnings are failures
echo 'pub fn add(a: i32, b: i32) -> i32 { a + b }' | rustcheck check --deny-warnings

# machine-readable, inside the sandbox
rustcheck check --json --require-sandbox < generated.rs

# is this machine able to verify at all?
rustcheck doctor

# repair mechanical errors using the compiler's own suggestions (no model)
rustcheck fix broken.rs --write

# type-check a solution together with a #[test] harness
rustcheck check --crate-type test solution_with_tests.rs
```

The `fix` loop applies only edits rustc marks `MachineApplicable`, from the end
of the source backwards so offsets stay valid, and stops when it runs out of
suggestions. It repairs conversions, missing `mut`, wrong argument order — the
things a model gets wrong mechanically. It cannot repair design mistakes.

Example report:

```json
{
  "success": false,
  "exit_code": 1,
  "duration_ms": 41.2,
  "sandbox": "bwrap",
  "timed_out": false,
  "safety_violation": null,
  "error_codes": ["E0308"],
  "errors": [
    {
      "level": "error",
      "code": "E0308",
      "message": "mismatched types",
      "line": 1,
      "column": 26
    }
  ],
  "stderr": "..."
}
```

Exit codes: `0` pass, `1` compile error, `2` policy guard rejection,
`3` timeout, `4` toolchain problem, `64` bad command line. Usage errors return
`64` rather than clap's default `2`, so a script can tell "the code broke the
policy" from "you called the tool wrong".

## External crates

Without `--dep` a snippet is checked against `std` only: `use serde_json::json;`
fails with `E0433`, because a bare `rustc` has no rlib to point at.

```bash
# one crate, any published version
echo 'use serde_json::json; pub fn f() -> serde_json::Value { json!({}) }' \
  | rustcheck check --dep serde_json@1

# several crates, with a test harness
rustcheck check --dep tokio@1 --dep serde@1 --crate-type test solution.rs

# repair a snippet that uses a crate
echo 'use serde_json::Value; pub fn n(v: &Value) -> u16 { v["a"].as_u64().unwrap_or(0) }' \
  | rustcheck fix --dep serde_json@1
```

The first run creates a throwaway Cargo project under `~/.cache/rustcheck/`
(`$XDG_CACHE_HOME`, or `$RUSTCHECK_CACHE_DIR` to override), builds the requested
crates once, and records where the artifacts landed. Later runs only read that
manifest, so the compiler stays the slow step: ~43 ms with `serde_json` in
scope versus ~36 ms for a std-only snippet. `--dep name@1.2` pins a version;
`@` and `=` are both accepted, and `name` alone means any version.

Cargo runs outside the sandbox because it has to reach the registry. The
snippet never does: `rustc` still runs under `bwrap`, with only the artifact
directories bound in, read-only.

Limits worth knowing before you rely on it:

- **Registry crates only** — `path:` and `git:` dependencies are rejected
  rather than half-supported.
- **One source file** — `mod foo;` pointing at another file will not resolve.
- **Type checking is not correctness** — code that compiles can still be wrong.
- A dependency that will not resolve is reported as `E_DEPS` with exit code
  `4`: the tool could not do its job, which is not the same as bad code.

## Policy guard

`--guard` is off by default because legitimate Rust uses `unsafe` and I/O.
Enable it only for untrusted snippets that are supposed to stay pure. It is a
coarse filter, not a security boundary — the sandbox is the boundary.

## What the sandbox does and does not do

`rustc` runs under `bwrap --unshare-all --die-with-parent`, with `/usr`, the
C-library directories, the Rust toolchain and the dependency cache bound in
read-only, a fresh `tmpfs` on `/tmp`, and no network. That matters for more than
resource limits: a snippet can say `include_str!("/home/you/.ssh/id_rsa")`, and
rustc would read it into a diagnostic that goes straight back to whoever is
driving the loop. Paths outside the binds are invisible — verified:
`include_str!("/etc/shadow")` fails with `ENOENT`.

Whether the sandbox can work at all is probed by running `rustc --version`
through it, once per process. `bwrap` can be installed and still be useless
(blocked user namespaces), and a rustup toolchain can live outside the paths a
naive sandbox exposes; either case would turn valid code into `fail`. In auto
mode a broken sandbox means an unsandboxed run plus `sandbox: "none"` in the
report; with `--require-sandbox` it is `E_NO_SANDBOX` and exit `4`.

What it does not do: with `--dep`, Cargo fetches and builds dependencies on the
host, outside the sandbox, because it needs the network. Named crates are
therefore trusted; the snippet is not.

Built and tested only with `rustc 1.99.1` on x86_64 Linux. No `rust-version`
